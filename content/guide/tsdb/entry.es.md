Una base de datos de series temporales guarda **puntos**: una marca de tiempo, un valor y unas pocas etiquetas como host o región. Cada combinación distinta de un nombre de métrica y sus etiquetas es una **serie**. Servidores, dispositivos y aplicaciones envían puntos cada pocos segundos, así que la base está hecha para un flujo constante de pequeñas inserciones y para consultas que piden un rango de tiempo, como la última hora de CPU de cada host.

Dos números la dimensionan. El primero son los **puntos por segundo**: la ingesta tiene un techo por instancia, y una flota que informa a menudo puede superarlo. El segundo es la **cardinalidad**, el número de series distintas. Cada serie necesita una entrada en el índice, así que una etiqueta con valores sin límite, como un id de usuario, puede multiplicar el número de series de un día para otro. El simulador modela ambos: las escrituras por encima de `points_per_s` se encolan y fallan, y por encima de `series_limit` las escrituras primero se ralentizan y luego se rechazan. Una explosión de cardinalidad es uno de los eventos de caos. Las consultas de rango cuestan más cuanto más largo es el periodo que cubren.

Los puntos en bruto suelen guardarse un tiempo limitado y después se borran o se reducen a agregados de menor resolución. `retention_days` deja constancia de esa decisión en la tarjeta; el simulador no ejecuta trabajos de retención.

**Cómo lo factura el simulador.** InfluxDB, TimescaleDB y Mimir funcionan en un nodo a 260 $ al mes cada uno. Amazon Timestream no cobra por nodo: cobra 0,50 $ por millón de puntos escritos y 0,01 $ por millón de unidades de consulta (precios didácticos; fuente por confirmar).

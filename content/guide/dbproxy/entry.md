Every open connection to a SQL database costs it memory and a process or thread, so databases cap them with `max_connections`. An app usually keeps a pool of connections per instance. That works for a few instances, but when autoscaling adds dozens, or serverless functions each open their own, the total passes the cap and new connections fail exactly when traffic peaks.

A connection pooler sits between the app and the database. It accepts many cheap client connections and shares a small set of real **server connections**, `pool_size`, among them. In **transaction mode** a client borrows a server connection only for the length of one transaction, so a few dozen connections can serve thousands of mostly idle clients. In **session mode** a client keeps its server connection for as long as it is connected, which saves little. Transaction mode breaks session features such as temporary tables or advisory locks, which is the main design trade-off.

When a problem turns on connection limits, the simulator models it: each app slot talking straight to SQL holds a database connection and connections past the limit fail; through a pooler, calls share the pool, pay a small delay and queue when every pooled connection is busy. The pooler's own cap on client connections, `client_limit`, is a design note only.

**How the simulator bills this.** A self-hosted pooler (PgBouncer, ProxySQL, VTGate) runs on a small node at $30 a month. Amazon RDS Proxy is priced per vCPU-hour of the database behind it; the simulator uses $45 per instance a month as a stand-in (teaching prices; source to be confirmed).
